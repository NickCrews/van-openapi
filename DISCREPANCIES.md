# Deviations from the official docs

Generated by `make discrepancies` from the `x-docs-discrepancy` fields in
[openapi.json](openapi.json) — do not edit by hand.

The spec itself records only observed behavior; this file records where that
behavior deviates from the official docs at <https://docs.ngpvan.com>.
Research status and evidence live in `x-provenance` fields and
[STATUS.md](STATUS.md).

- **GET /people/{vanId} parameter `vanId`** — Official docs type this path parameter as string (default "100476252"); the route only matches integers — a non-integer segment returns an IIS HTML 404 page (observed 2026-08-03).
- **GET /people/{vanId} parameter `$expand`** — Official docs list only 10 valid $expand values; the API's own INVALID_PARAMETER hint (observed 2026-08-03) lists these 23.
- **POST /people/find** — Official docs imply a 200 with a person object on match. Sandbox probing (2026-08-03) shows 302 + Location on match and 404 with a match stub on no match; no 400 was observed even for sparse criteria like firstName-only. Criteria below the documented minimum combinations are also answered 404 Unmatched rather than rejected, so under-specified requests are indistinguishable from genuine no-matches. The docs are also silent on ambiguous matches: when several person records satisfy the criteria the API returns one of them with no indication that others matched.
- **POST /people/findOrCreate** — The docs present the minimum match combinations as a matching quality note; in practice, on this endpoint, falling short of them is what silently produces duplicate person records (observed 2026-08-04).
- **PUT /people/{vanId}/mergeInto** — Official docs say emails, phones and addresses are all combined into the primary, which holds — though a merged-in address is normally invisible afterwards, since $expand=addresses surfaces only the best Voting and Mailing address and the primary's own takes both slots (POST /people/find still matches it). The docs are silent on four further behaviours: duplicate emails and phones are collapsed rather than doubled, the primary can lose its preferred email address to a more recently added one coming from the secondary, notes move to the primary, and unknown vanIds are answered 400 rather than 404 (observed 2026-08-06).
- **PUT /people/{vanId}/mergeInto parameter `vanId`** — Official docs place no constraint on this parameter; a negative id returns 500 rather than a validation error, and a non-integer segment matches no route and returns an IIS HTML 404 page (observed 2026-08-05).
- **PUT /people/{vanId}/mergeInto parameter `whatIf`** — Official docs type this as a plain boolean and say "if true, simulates the merge request without actually executing the merge", implying any truthy value is safe. Only case-insensitive `true` simulates: `whatIf=1`, `whatIf=yes` and `whatIf=xyz` each performed a real, irreversible merge, and `whatIf=` returned 400 (each value confirmed on its own freshly created pair, 2026-08-05).
- **PUT /people/{vanId}/mergeInto (responses / 200)** — Official docs document only the JSON body; the response also carries a Location header pointing at the surviving primary (observed 2026-08-05).
- **GET /people/{vanId}/notes parameter `vanId`** — Official docs type this path parameter as string (default "100476252"); the route only matches integers — a non-integer segment returns an IIS HTML 404 page (observed 2026-08-04).
- **POST /people/{vanId}/notes parameter `vanId`** — Official docs type this path parameter as string (default "100476252"); the route only matches integers (observed 2026-08-04).
- **PUT /people/{vanId}/notes/{noteId} parameter `noteId`** — Official docs type this path parameter as string (default "225"); the route only matches integers (observed 2026-08-04).
- **GET /surveyQuestions parameter `$top`** — Official docs claim a default of 40; the API's own INVALID_PARAMETER hint (observed 2026-08-03) states default 50, maximum 200.
- **components/responses/TooManyRequests** — The official docs do not mention rate limiting or the 429 response anywhere in their reference index (checked 2026-08-04). Observed live on GET /surveyQuestions and POST /people/create.
- **schema `PersonMatchCriteria.phones`** — The docs list only an email address as a criterion sufficient on its own; a phone number alone also matched (observed 2026-08-04, sandbox vanId 102719047).
- **schema `PersonMatchPhone.countryCode`** — Official docs spell this field 'countyCode' — likely a typo in the docs; not yet verified live.
- **schema `NoteContactHistoryInput`** — Official docs type all four fields as strings; that is what has been probed and what this schema keeps, but whether integers are also accepted has not been tested (2026-08-04).
- **schema `PersonPhone.phoneType`** — Official docs document only the write codes and imply they are echoed back. GET returns an expanded category name instead, and seven write codes collapse onto three of them (observed 2026-08-03).
- **schema `PersonPhone.deviceType`** — Official docs document only the write codes C, L, U, F, V and imply they are echoed back; GET returns the spelled-out names Cell/Landline/Unknown/Fax/VoIP (observed 2026-08-03).
- **schema `PersonPhone.isBest`** — The official common models do not document isBest for phones; it is returned on every phone, and is awarded to at most one number per person — not one per phoneType — by a phoneType/deviceType ranking rather than by recency alone (observed 2026-08-06).
- **schema `PersonPhone.phoneOptInStatus`** — Official docs describe the field only as the write codes I/U/O; GET returns the expanded names Opt-In/Unknown/Opt-Out (observed 2026-08-03).
- **schema `PersonPhone.isCellStatus`** — The value written is validated but never read back: phones written with a valid isCellStatus still return null from GET /people/{vanId}?$expand=phones (observed 2026-08-03).
- **schema `PersonAddress.type`** — Official docs list five address types with no indication that reads are restricted; $expand=addresses only ever returns Voting and Mailing, and Work and Custom addresses are omitted from the response entirely (observed 2026-08-03).
- **schema `PersonPhoneInput.phoneType`** — Official docs list five codes (H, W, C, M, F); the API's own INVALID_PARAMETER response accepts seven — "'phoneType' must be one of: H, W, O, C, M, F, P" (observed 2026-08-03).
- **schema `PersonPhoneInput.deviceType`** — Official docs list only the letter codes. The API's INVALID_PARAMETER response also accepts numeric ids 1, 2, 4, 5, 6; writing 2 and 6 was confirmed to store Landline and VoIP (observed 2026-08-03). There is no id 3.
- **schema `PersonAddressInput.type`** — The value is not validated: an address written with type "Q" is accepted with 201 and filed as the person's home address (observed 2026-08-03).
- **schema `PersonInput.contactMode`** — Official docs say the value must be Person or Organization; it is not validated. Writing "Q" returns 201 and the person reads back with contactMode "Person" (observed 2026-08-03).
