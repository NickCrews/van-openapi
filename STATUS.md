## Field notes (from sandbox probing, 2026-08-03)

- **Auth**: HTTP Basic. Username = application name (anything works in sandbox; van-cli defaults to `default_user`), password = `{apiKey}|{databaseMode}`. Mode `0` = My Voters, `1` = My Campaign. Wrong mode → `401 {"errors":[{"code":"UNAUTHORIZED","text":"Invalid Database Mode"}]}`.
- **Error envelope**: `{"errors":[{"code","text","properties":[…],"hint"?}]}`. Seen codes: `UNAUTHORIZED`, `INVALID_PARAMETER`, `BAD_REQUEST`, `NOT_FOUND`, `429`.
- **Rate limiting (429)**: exceeding the key's rate-limit profile returns the standard error envelope with `code` the numeric string `"429"` (the only non-symbolic code seen) and text `"Rate limit exceeded. Try again in N ms."` — there is **no `Retry-After` header** (225 429s captured 2026-08-04, none carried one; the retry hint exists only in the text). Per-key, so any endpoint can return it: first surfaced by the fuzzer on `POST /people/create`, reproduced with ~300 concurrent `GET /surveyQuestions`. Spec'd as the shared `TooManyRequests` response on every operation. Rate limiting is absent from the official docs entirely (`x-docs-discrepancy` on the component).
- **Pagination envelope**: `{"items":[…],"nextPageLink":null|string,"count":int}` — but not universal: `/canvassResponses/contactTypes` returns a bare array.
- **`$top`**: default 50, max 200 per the `INVALID_PARAMETER` hint on `/surveyQuestions`.
- **`POST /people/find` does not behave as docs imply**: match → `302` with `Location: /v4/people/{vanId}` and body `{"vanId":int,"status":"Matched"}`; no match → `404` with `{"vanId":null,"status":"Unmatched"}` (even for sparse criteria like firstName-only — no 400 observed). `findOrCreate` → `201 {"vanId":int,"status":"UnmatchedStored"}`.
- **`POST /echoes`** accepts an empty body; all fields nullable in response (`{"message","dateSent","delayInMilliseconds"}`). **BUG**: `delayInMilliseconds: -1` hangs the connection indefinitely (likely passed straight into .NET as `Timeout.Infinite`); other negative values return 500.
- **Fuzzer-found 500s** (should be 400s): negative `delayInMilliseconds` on `/echoes`; non-ASCII filter values on `/surveyQuestions`; `vanId: 0` or `phones: [null]` on `/people/find`. Documented as 500 responses in the spec; `not_a_server_error` check disabled in `make fuzz`.
- **Redirect-following clients** (requests, fetch, httpx, schemathesis) see `POST /people/find` return **200 with the full person record** because they auto-follow the 302 to `GET /people/{vanId}`. The spec documents both the raw 302 and the followed 200.
- **Person field inventory** observed live via `GET /people/{vanId}` (~70 fields, most null on a minimal record — see the `Person` schema). `dateAcquired` is `0001-01-01T00:00:00Z` (dotnet default) for API-created records.
- **`POST /surveyQuestions`** requires all `*OtherLanguage` fields, `scope`, and a valid `type`; `Candidate`/`Issue`/`Volunteer`/`GOTV` all rejected as invalid type in the demo committee — valid values still unknown (blocker for seeding sandbox list data).
- **`GET /people/{vanId}`**: unknown, `0`, and negative ids all return the JSON `NOT_FOUND` envelope (contrast `/people/find`, which 500s on `vanId: 0`). A non-integer path segment misses the route and returns an **IIS HTML 404 page** (`text/html`) — documented as a second 404 media type in the spec.
- **`$expand` on `GET /people/{vanId}`**: 23 valid values enumerated by the API's own `INVALID_PARAMETER` hint (official docs list only 10): contributionHistory, addresses, phones, emails, codes, customFields, externalIds, preferences, recordedAddresses, reportedDemographics, suppressions, cases, customProperties, districts, electionRecords, membershipStatuses, notes, organizationRoles, scores, disclosureFieldValues, primaryContact, pollingLocation, biography. Expanded collections come back as `[]` when empty vs `null` when not expanded.
- **`$expand` on `GET /people` (search)** is a much smaller set — the hint names only Addresses, Emails, Phones, Districts, PollingLocation — and the hint over-promises: `pollingLocation` is refused with a differently-shaped error, `400 {"code":"BAD_REQUEST","text":"May not request 'pollingLocation' in this context"}` (no `properties`, no `hint`), alone or combined with other sections. Probed 2026-08-04 in My Campaign mode only; it may be expandable in My Voters. The usable set is addresses, emails, phones, districts, all captured as response examples on the operation.
- **Person write endpoints** — none are in the docs' page index (`llms.txt` lists only `/people/find`); paths come from van-cli `people.ts`, bodies from the docs' "Match Candidate" common model. All three take the same body (`PersonInput`) and answer with the same `{vanId, status}` stub:
  - `POST /people/create` → `201 {"status":"Stored"}`. **No de-duplication**: an exact copy of an existing person's name + email creates a second record. `POST /people/findOrCreate` → `302 Matched` on a hit, `201 {"status":"UnmatchedStored"}` otherwise — it never 404s. `POST /people/{vanId}` → `302 Matched`; unknown/0/negative id → `404`.
  - **Everything is optional.** `POST /people/create` and `/people/findOrCreate` both accept `{}` and create a blank, nameless record — van-cli enforces firstName/lastName client-side, the API does not.
  - A body `vanId` that exists short-circuits everything: even `create` returns `302 Matched` and writes nothing. `vanId: 0` is silently ignored here (contrast `/people/find`, which 500s on it).
  - **Update is a merge, not a replace**: omitted fields keep their values, and `emails`/`phones`/`addresses` are *appended* — sending the same email twice stores it twice. There is no way to remove a contact method through this endpoint.
  - **`isPreferred` behaves differently for emails and phones.** A newly added email takes the preferred flag off the previous one automatically, even when several already exist and none of the writes set the flag; a newly added phone does not — seven phones written with no flag all read back `isPreferred: false`.
  - **Validation is uneven.** Enforced: `sex` (M/F, case-insensitive), `contactMethodPreferenceCode` (P/E/M/F/S), `electionType` (10 codes), `dateOfBirth` century, every max length (`firstName` 75, `title` 10, `party` 1, `cycle` exactly 4, `ext` 6), email format, phone number validity. **Not** enforced: `contactMode` (any value → stored as `Person`), `party` (any single character stored verbatim), address `type`, and an unparseable `dateOfBirth` (silently dropped to null rather than 400).
  - Context-scoped lookups reject cleanly with 400 in the demo committee — `customFieldValues.customFieldId`, `selfReportedRaces.reportedRaceId`, `identifiers.type` — so those write paths could only be observed failing. **BUG**: `identifiers` with the *valid* type `dwid` returns 500, not 400.
- **Contact sub-models** (`PersonEmail`, `PersonPhone`, `PersonAddress`, `PhoneIsCellStatus`) and their write-side twins (`PersonEmailInput`, `PersonPhoneInput`, `PersonAddressInput`) — split because the same field name carries different value domains in each direction (`phoneType: "C"` in, `"Personal"` out), which `readOnly` cannot express. Enums pinned down by writing every documented code through `POST /people/findOrCreate` and reading it back with `$expand`:
  - **Emails read back the codes they were written with** (`type` P/W/O, `subscriptionStatus` U/N/S). **Phones do not**: writes take single letters, reads return words. `phoneType` H/C/M/P → `Personal`, W/F → `Work`, O → `Other`; `deviceType` C/L/U/F/V → `Cell`/`Landline`/`Unknown`/`Fax`/`VoIP`; `phoneOptInStatus` I/U/O → `Opt-In`/`Unknown`/`Opt-Out`. Writing `phoneType: "C"` also sets `deviceType: "Cell"`, and `"F"` sets `"Fax"`.
  - `isSubscribed` is a lossy projection of `subscriptionStatus`: `S`→true, `U`→false, `N`→**null** (neutral has no boolean form). Writing `isSubscribed: false` stores `U`, which is terminal.
  - Undocumented **read-only phone fields**: `dateCreated`, `isBest`, `isDisclosure`, `smsOptInStatus` (mirrors `phoneOptInStatus`), `isCellPhoneExchange`, `tags`.
  - **Nulls are rarer than they look** (probed 2026-08-04 with minimal writes, explicit-null writes, and a blank `{}` person): the server substitutes defaults instead of storing null. Phones: only `ext`, `isCellStatus` and `tags` can be null — everything else defaults (`phoneType` `Personal`, `deviceType` `Unknown`, opt-in statuses `Unknown`, `dialingPrefix`/`countryCode` from the context). Emails: `type` defaults `P` and `isPreferred`/`dateCreated` are always set, but `subscriptionStatus` **can** read back null (four older non-preferred addresses on `102714580` have it — rule unknown; a fresh write without it defaults `S`), and `isSubscribed` is null both there and for the `N` mapping. Addresses: `city`/`stateOrProvince` are inferred from the zip, a missing zip reads back `""` (empty string, not null), and an address too sparse or unresolvable to standardize (street line only, or an unknown zip) is silently not stored/surfaced at all. Person: even a blank record has `contactSource`, `contactMode`, `formalSalutation` (`"Friend"`), `formalEnvelopeName` (`"Our Friend At"`), `isDeceased`, `dateCreated` and `dateAcquired` — but plain `salutation`/`envelopeName` *are* null on it. Spec tightened accordingly.
  - Undocumented **read-only address fields**: `unitNo`, `geoLocation`, `preview`, `streetAddress`, `displayMode` (only `"Standardized"` seen).
  - `$expand=addresses` returns **at most two entries** — best known Home (typed `Voting`) and best known Mailing — with the *same* `addressId` repeated when one address fills both roles. Addresses written as `Work` or `Custom` are stored but never surfaced by this expansion. The written `type` is not validated at all: `"Q"` is accepted with 201 and filed as the home address.
  - `isCellStatus` is validated on write (`statusId` 1–4, `statusName` `Verified Cell`/`Likely Cell`/`Likely Not a Cell`/`Not a Cell`, and a mismatched id/name pair is accepted) but always reads back `null`. `GET /phones/isCellStatuses` exists and returns a bare array — empty in the sandbox.
- **`GET /people` (search)** — absent from the official docs' page index; path and parameter list from van-cli `people.ts`. Returns full `Person` records in the standard pagination envelope (`count` = total matches, `nextPageLink` an absolute URL with an explicit `:443` port). Probed 2026-08-04:
  - Requires at least one **search** parameter — firstName, lastName, middleName, streetAddress, city, stateOrProvince, zipOrPostalCode, phoneNumber, email, commonName, officialName — otherwise 400 `INVALID_PARAMETER` "This endpoint requires at least one search parameter to be set.", even when filter/paging parameters are present.
  - Text criteria are case-insensitive **prefix** matches (`lastName=Testpers` hits "Testperson"; `estperson` does not). `email` matches against all of a person's addresses, not just the preferred one. Non-ASCII values just return 0 results — no `/surveyQuestions`-style 500.
  - `phoneNumber` is validated: non-numerics stripped, then must match the NANP regex `^1?[2-9][0-8]\d[2-9]\d{6,6}$` (from the API's own hint), else 400.
  - `contactMode` filters to Person/Organization records but does **not** count as a search parameter, and an invalid value is silently ignored. `employer`, `occupation` and `dateOfBirth` are accepted but do nothing at all (even `dateOfBirth=notadate` passes silently).
  - `$top` default 50 / max 200 — van-cli caps people search at 50 client-side, but that limit is not server-side. `$skip` must be ≥ 0. `$orderby` accepts only `Name` (and `Name desc`). For `$expand` see the dedicated bullet above (usable set: addresses, emails, phones, districts).
  - **Person schema discoveries** (fuzzer-found on this endpoint, apply to the shared schema): search results return `formalSalutation`/`formalEnvelopeName` as **null** even for records where get-by-id derives them; and there is a `partialDateOfBirth` `{month, day, year}` field on both search and get-by-id responses — missed by earlier field inventories because it is null whenever `dateOfBirth` is null.
- **BUG (request escapes the API)**: a path segment containing `<`, `>`, `*` or `&` (e.g. `GET /people/1%3E`) trips ASP.NET request validation before routing, and the request is handed to the **VAN web application** instead: `302` → `Location: /Error.aspx?EID={code}` with an HTML "Object moved" body; following it gives `200 text/html` (the "Oops...something went wrong" page). So a JSON-only endpoint can answer `200` with HTML. Neighbouring characters take three other paths: `:` and `"` → IIS HTML 404, `\` → JSON 404 envelope, plain non-integer (`abc`) → IIS HTML 404. Found by the stateful fuzz phase; spec'd as the shared `RequestValidationRedirect` response plus a `text/html` variant on the 200s.
- **Transient 502**: one fuzz run (2026-08-04) caught a bare nginx `502 Bad Gateway` HTML page from `POST /people/find` (payload had `dateOfBirth: [null, null]`); the identical request returned 400 on three immediate retries. Treated as infrastructure flakiness, not API behavior — deliberately not spec'd, but it can turn a `make fuzz` run red once in a while.
- **BUG (stack-trace disclosure)**: a query-string key containing `[` (e.g. `?a[=1`) crashes ASP.NET's jQuery-syntax key parsing → 500 with a raw `{"message","exceptionMessage","exceptionType","stackTrace"}` payload — full server stack trace leaked, and a different body shape than the standard envelope. Found by the stateful fuzz phase on `GET /people/{vanId}`; the shared 500 response now accepts both shapes (`AspNetError` schema).
- **Stateful testing**: the spec now defines OpenAPI `links` from `POST /people/find` (302 and redirect-followed 200) to `GET /people/{vanId}` via `$response.body#/vanId`; schemathesis's stateful phase picks them up automatically in `make fuzz`. The write endpoints add links from their 201/302 responses to `getPerson`, taking the total to 15 (8 of them inferred by schemathesis itself) across ~195 scenarios — but only **1 is actually covered** per run. The 200-response links can't be exercised by schemathesis's raw (non-redirect-following) client, and the rest simply aren't reached at this example budget; worth revisiting if stateful coverage matters more than wall-clock.
